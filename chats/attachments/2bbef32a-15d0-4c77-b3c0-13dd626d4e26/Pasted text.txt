Earlier implementation used:

For a correct controller, use current UGV orientation from odometry and compute:

If the adapter currently does not consume odometry orientation, this is a good

# Context summary from the project and this chat

The project started as a Python prototype with modules such as `core`, `vision`, `mission`, and `swarm`. During review, the architecture was converted into proper ROS 2 packages because the original prototype depended heavily on simulated coordinate changes, ad-hoc communication, and String-based protocols. The current project goal is a ROS 2 Jazzy academic multi-UAV/UGV simulation whose complete high-level flow is **UGV → deployment → UAV search → detection → target tracking/fusion → assignment → standoff → operator RETURN/HOLD → return/docking**. That exact flow is also stated in the V0.2 README. combined_workspace_text_Entire\_…

The resulting architecture separated interfaces, vehicles, perception, targets, swarm coordination, mission management, visualization/core utilities, simulation assets, and bringup. Tracking was deliberately consolidated into `wildlife_targets`; the system is built around a stable detector-independent `Detection` contract. combined_workspace_text_Entire\_…

## Evolution from prototype to V0.1

The original project roughly looked like:

```text
wildlife_ws/
├── app.py
├── config.py
├── modules/
│   ├── core/
│   ├── mission/
│   ├── swarm/
│   └── vision/
├── simulator/
├── static/
├── templates/
└── logs/
```

Important weaknesses identified in that early implementation were:

- mission expected fused detections but there was not a proper fusion implementation;
- “YOLO” behavior was actually synthetic distance/probability logic rather than image inference;
- multiple commands were encoded as strings;
- target assignment was simplistic;
- UGV/deployment responsibilities were mixed;
- vehicle motion consisted mainly of coordinate updates rather than real simulated dynamics;
- the architecture did not yet cleanly separate interfaces, simulation and vehicle integration.

The architecture was therefore reorganized into ROS packages with typed messages/services/actions.

V0.1 introduced the first full ROS 2 package scaffold, including:

```text
wildlife_interfaces
wildlife_core
wildlife_perception
wildlife_tracking
wildlife_targets
wildlife_swarm
wildlife_mission
wildlife_vehicles
wildlife_simulation
wildlife_bringup
```

It implemented a logic-level simulation, not a finished Gazebo/PX4 stack.
